# PROCESS LAB · руководство Камилы (Backend / Simulation)

**Актуальный фронтенд:** КПСЦ Studio v2 · `frontend/index.html`, `styles.css`, `app.js`.
**Кейс:** цифровой двойник предприятия (фабрика процессов: 9 сборочных операций + ОТК).
**Запуск:** локально, Python 3.9+; нет `pip install` и нет внешних сервисов.

## 1. Что добавить в уже существующий GitHub-репозиторий

Не создавайте второй репозиторий. Откройте ваш существующий `process-lab` через VS Code.

1. Из архива перенесите `backend/`, `data/`, `tests/test_engine.py`, `tests/test_api.py`, `docs/` в **корень** репозитория. Если `tests/` уже есть, **объедините** папки, не удаляя её содержимое.
2. Перенесите `frontend/backend_sync.js` рядом с вашим `frontend/app.js`.
3. В `frontend/index.html` **после** строки `<script src="./app.js" defer></script>` поставьте `<script src="./backend_sync.js" defer></script>`.
4. Ваши `frontend/app.js`, `frontend/styles.css` и остальные файлы **не заменяйте**. В полном ZIP лежит проверенная версия целиком — на случай, если удобнее начать с неё.
5. Коммит в GitHub: `Add Python simulation API and integration bridge`.

## 2. Как запустить из VS Code (важно: НЕ Live Server!)

Откройте терминал `Terminal → New Terminal` в VS Code. Убедитесь, что текущая папка — **корень `process-lab`**, где видны `backend/` и `frontend/`.

**Mac:**

```bash
python3 -m backend.server
```

**Windows:**

```powershell
py -m backend.server
```

Откройте браузер по адресу:

**http://127.0.0.1:8765/**

На верхней панели сайта будет статус **«Python API · локальная демо-модель»**. Нажмите «Симуляция» — запрос пройдёт в `backend/engine.py`.

Чтобы выключить сервер, нажмите `Ctrl+C` в терминале.

Если сайт открыть через Live Server, он останется в резервном режиме **JavaScript**, и Python-запросы выполняться не будут. Это нормально: в таком случае фронтенд сам себя рассчитывает.

### Если порт занят

```bash
python3 -m backend.server --port 8766
```

После запуска откройте `http://127.0.0.1:8766/`. Не используйте `python3 backend/server.py`: относительные импорты могут не сработать.

## 3. Что реально работает

- Проверка схемы на отсутствующие узлы, неверные числовые поля, дублирующие связи, циклы и неправильное соединение ОТК с заказчиком.
- Запуск дискретно-событийной модели с заданным периодом и случайными колебаниями времён (воспроизводимое зерно `seed`).
- Производственная сеть с **ветвлениями и синхронизацией подсборок**: к операциям №4 и №7 подходят независимые входы.
- Количество сотрудников, циклы, доступность, переналадка, брак, партии, начальный НЗП, один или несколько логистов.
- Перевозки по **условной физической планировке** и ограничение транспортной партии.
- Подсчёт выпуска, недосдачи, НЗП, загрузки, очередей, ожиданий, рейсов и затрат (по демонстрационным ставкам).
- API для проверки, симуляции и сравнения двух JSON-моделей.
- Вывод дополнительных **оценочных** показателей КПСЦ: критический путь, оценка полезного времени, теоретическая производительность операций.
- Сохранён исходный браузерный режим: при отсутствии Python-сервера сайт продолжает работать локально.

## 4. Что НЕ реализовано и не следует обещать жюри

1. **Нет реальных производственных замеров.** `data/factory_demo_v3.json` воспроизводит исходную модель сайта; числовые параметры — учебные допущения.
2. **Поля `kpsc.meta`:** партия обработки, количество оборудования, документируемый простой, затраты операции, складские запасы и признак добавления ценности пока НЕ управляют дискретно-событийной моделью. Метрики из этих полей — справочные. Отдельные времена простоев не прибавляются повторно поверх `availability`.
3. **Информационные связи `kpsc.infoLinks`** отображаются, но не влияют на выпуск и очереди — не следует путать их с материальными ребрами `edges`.
4. **Реальные маршруты логиста** не восстановлены: применяются прямые расстояния × коэффициент, без обхода оборудования, погрузочных ограничений и обратного движения в конкретной последовательности.
5. **НЗП по рёбрам** подсчитывает подсборки; нельзя выдавать его за количество готовых изделий.
6. **Брак** списывается из потока; фактические возвраты на конкретную операцию для доработки ещё не реализованы.
7. **Финансовая модель** — приблизительная: входные тарифы условные, стоимость материала начисляется на запущенные комплекты, а выручка — на отгруженные.
8. **Нет защищённой аутентификации и серверной БД**; сценарии по-прежнему сохраняются в локальном хранилище браузера и могут передаваться через JSON. Локальный прототип доступен только с `127.0.0.1`.

Для финального этапа после согласования с заказчиком: подключить фактические замеры, уточнить учёт подсборок и брака, добавить модель логистического маршрута, хранение сценариев с авторизацией.

## 5. Тесты

```bash
python3 -m unittest discover -s tests -v
```

Автотесты проверяют API, входные ограничения, ветвления графа, воспроизводимость расчётов и разделение КПСЦ/физической планировки. Контрольное значение исходной **демо-модели**: 9 принятых из 10, 68 модельных рейсов, 24 единицы НЗП/подсборок на конец смены; это не фактические показатели фабрики.

Можно проверить API отдельно:

```bash
curl http://127.0.0.1:8765/api/v1/health
```

Больше примеров в `docs/API_CONTRACT.md`.
